# Contributing

There are many types of contributions you could do. Contributions are very welcome!
Every little bit helps, and credit will always be given.

Below we will outline how you can contribute to pixelator. If you want to learn more about
how to setup a development environment for pixelator see [DEVELOPERS.md](DEVELOPERS.md).

## Pull requests

Open pull requests against `dev`. They are **squash-merged**, and the **PR title becomes the commit message**.
Releases are generated from these messages, so the title must follow
[Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<optional scope>): <description>
```

| Type | Use for | Version bump | In changelog |
| --- | --- | --- | --- |
| `feat` | New feature | minor | yes |
| `fix` | Bug fix | patch | yes |
| `perf` | Performance improvement | patch | yes |
| `revert` | Revert a previous change | patch | yes |
| `refactor`, `docs`, `test`, `build`, `ci`, `chore` | No user-facing change | none | no |

- Mark a breaking change with `!` (`feat!: drop Python 3.11`) or a `BREAKING CHANGE:` footer. This bumps the major version.
- Use the scope for the area of the code (`feat(pna): ...`, `fix(cli): ...`).
- Keep the description short and in the imperative mood, since it becomes the changelog entry.
- A CI check validates the title of every PR.

## Changelog and releases

Do **not** edit `CHANGELOG.md` or bump any version in a PR. The changelog is generated by
[release-please](https://github.com/googleapis/release-please), which keeps a release PR open on `dev`.
Merging that PR creates the `vX.Y.Z` tag and the GitHub Release, which publishes the package to PyPI,
deploys the docs and builds the release container images. `main` is then fast-forwarded to the tag.

The package version is derived from the git tag (`hatch-vcs`), so there is no version to edit in the repository.

## Types of Contributions

### Report Bugs

Report bugs at https://github.com/PixelgenTechnologies/pixelator/issues

If you are reporting a bug, please include:

* Your operating system name and version.
* Any details about your local setup that might be helpful in troubleshooting.
* Detailed steps to reproduce the bug.

### Fix Bugs

Look through the Github issues for bugs. Anything tagged with "bug" and "help
wanted" is open to whoever wants to implement it.

### Implement Features

Look through the Github issues for features. Anything tagged with "feature", "improvement",
"enhancement" and "help wanted" is open to whoever wants to implement it.

Any new feature is tagged with "feature" and "improvement" if it is already implemented and
looking for improvements, but if the feature doesn't exist, we will tag it with "feature" and
"enhancement".

### Write Documentation

Pixelator could always use more documentation, whether as part of the
official Pixelator docs, in docstrings, or even on the web in blog posts,
articles, and such.

### Submit Feedback

The best way to send feedback is to file an issue at https://github.com/PixelgenTechnologies/pixelator/issues

If you are proposing a feature:

* Explain in detail how it would work.
* Keep the scope as narrow as possible, to make it easier to implement.

### Get in contact with the Pixelgen Support team

If your question is not specifically related to Pixelator but you have a questions about
Pixelgen Technologies or our products, you can contact us through our [support site](https://www.pixelgen.com/support/).
